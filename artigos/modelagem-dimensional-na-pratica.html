Modelagem dimensional na prática: as decisões por trás do meu pipeline ETL

Quando comecei a montar um pipeline de ETL do zero para praticar fora do trabalho, a primeira tentação foi pular direto para o código: ler o CSV, jogar numa tabela, conectar o Power BI e pronto. Funciona para um protótipo, mas não é o que sustenta um dashboard de verdade. A parte que mais me ensinou não foi o Python, foi decidir como modelar os dados antes de escrever a primeira linha de transformação.

Usei o dataset público da Olist (cerca de 100 mil pedidos de um marketplace brasileiro, espalhados em 8 tabelas normalizadas) para construir um pipeline ETL completo, do CSV bruto até um modelo pronto para Power BI. Este artigo é sobre as decisões de modelagem, não sobre o código em si.

O problema do dado normalizado

No formato original, responder “qual a taxa de atraso de entrega por estado?” exige juntar pedidos, clientes e itens a cada consulta. Isso não escala para um dashboard: toda visualização vira uma query nova com cinco joins. A solução clássica é um star schema: dimensões que descrevem o contexto (cliente, produto, vendedor, data) e tabelas fato que guardam os eventos mensuráveis (pedidos, itens vendidos), já pré-juntadas na granularidade certa.

Por que duas tabelas fato, não uma

O primeiro instinto é criar uma fato só. Mas um pedido tem campos que fazem sentido no nível do pedido (valor total pago, nota de avaliação, atraso na entrega) e campos que só existem no nível do item (preço unitário, frete, vendedor). Colocar tudo em uma fato no grão de item obriga a repetir o valor pago e a nota em cada linha de item do mesmo pedido — e qualquer soma de “receita” feita ingenuamente no Power BI conta esse valor várias vezes.

A solução foi ter duas tabelas fato em grãos diferentes:

  • fact_orders — uma linha por pedido: pagamento, parcelas, nota, tempo de entrega.
  • fact_order_items — uma linha por item de pedido: preço, frete, ligado a produto e vendedor.

As duas compartilham as mesmas dimensões (cliente, data), então o Power BI consegue cruzar as duas sem problema — é só cuidado na hora de montar visuais que misturem métricas dos dois grãos.

Surrogate keys em vez dos IDs originais

O dataset usa IDs de texto (hash) como chave primária. Funciona, mas junções por string são mais lentas e o motor de compressão do Power BI (VertiPaq) fica menos eficiente com colunas de alta cardinalidade em texto. Troquei por chaves substitutas inteiras sequenciais em cada dimensão:

dim.insert(0, "customer_sk", dim.index + 1)

É uma linha de código, mas é a diferença entre um modelo que qualquer ferramenta de BI relaciona de forma eficiente e um que força concatenação de strings gigantes.

O que isso muda na prática

No trabalho, isso aparece toda vez que preciso desenhar uma nova fonte de dado para o Power BI: antes de escrever a primeira query no Azure Data Factory, vale a pena perguntar qual é o grão de cada fato e quais dimensões realmente se repetem. Errar essa parte não quebra o pipeline, mas produz números errados de forma silenciosa — o tipo de bug que só aparece quando alguém do time de negócio pergunta “por que esse total não bate com a planilha”.
